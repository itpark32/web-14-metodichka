# Безопасность веб-приложения

<p class="reading-time">Чтение: 11 минут</p>

Безопасность строится слоями. Клиентская проверка улучшает UX, но доверенная проверка выполняется на сервере.

## Основные угрозы

### XSS

Вредоносный ввод исполняется как JavaScript. Не вставляйте непроверенные строки через `innerHTML` или `dangerouslySetInnerHTML`, экранируйте вывод по контексту и используйте Content Security Policy.

### CSRF

Чужая страница заставляет браузер отправить авторизованный запрос. Защита: CSRF-токен, `SameSite` cookie и проверка происхождения.

### SQL injection

Данные меняют смысл SQL-запроса. Защита: подготовленные запросы и параметризация.

### Ошибки доступа

Скрытая кнопка не является защитой. Сервер проверяет право на каждый объект и действие, включая идентификатор из URL.

## Пароли и токены

- пароль хешируется `password_hash`, а не шифруется вручную;
- секреты лежат вне репозитория;
- токен имеет короткий срок и минимальные права;
- cookie сессии использует `HttpOnly`, `Secure`, `SameSite`;
- после входа и смены уровня доступа сессия обновляется.

## Загрузка файлов

Проверяйте размер, MIME-тип, расширение и содержимое. Генерируйте имя на сервере, храните вне исполняемой директории и не доверяйте исходному пути.

## CORS

CORS управляет тем, какие origin могут читать ответ в браузере. Это не механизм аутентификации и не защита серверного API от прямых запросов.

## Заголовки

Полезны CSP, `X-Content-Type-Options`, `Referrer-Policy`, HSTS и ограничения iframe. Конкретная политика зависит от приложения.

## Мини-задача

Проведите threat modeling магазина: активы, точки входа, роли, пять вероятных угроз и проверяемая защита для каждой.
