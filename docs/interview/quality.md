# Интервью: тестирование и архитектура

<p class="reading-time">11 ключевых вопросов с короткими ответами</p>

??? question "Unit, integration и E2E?"
    Unit изолирует небольшой модуль, integration проверяет несколько частей вместе, E2E проходит пользовательский сценарий через систему. Нужен баланс скорости, реалистичности и стоимости поддержки.

??? question "Что тестировать в React-компоненте?"
    Наблюдаемое поведение: что пользователь видит и может сделать. Ищите по роли и доступному имени, не проверяйте внутренний state.

??? question "Mock, stub и spy?"
    Stub дает подготовленный ответ, mock задает ожидания взаимодействия, spy наблюдает вызовы существующей функции. Термины могут различаться между библиотеками, важна цель подмены.

??? question "Как тестировать запрос?"
    Перехватить HTTP через MSW, запустить компонент как обычно и проверить loading, success, empty и error. Это меньше связывает тест с реализацией клиента.

??? question "Что такое tree shaking?"
    Сборщик удаляет неиспользуемые экспорты при статически анализируемых ES Modules и совместимом коде пакета.

??? question "Зачем делить bundle на чанки?"
    Чтобы не загружать код до момента, когда он нужен. Часто делят по маршруту или тяжелой функции, сохраняя баланс между размером и числом запросов.

??? question "Что измеряет LCP?"
    Время отображения крупнейшего видимого элемента контента. На него влияют сервер, приоритет ресурса, размер изображения, блокирующие стили и рендер клиента.

??? question "Что вызывает лишние рендеры?"
    Новые props-ссылки, изменение context, слишком высоко поднятый state и неустойчивые селекторы. Сначала подтвердите проблему Profiler.

??? question "Vite и Webpack?"
    Vite использует нативные ESM для быстрого dev server и Rollup-сборку. Webpack строит граф и дает очень гибкую систему loaders/plugins. Выбор зависит от проекта.

??? question "Как выбрать архитектурную границу?"
    Группируйте код по причине изменения и направляйте зависимости от UI к бизнес-правилам и внешним адаптерам. Граница должна уменьшать связанность.

??? question "Что проверяете на code review?"
    Корректность, читаемость, тесты, безопасность, доступность, производительность, совместимость и соответствие задаче. Комментарий объясняет риск, а не только предпочтение.
