# 41. Архитектура веб-приложений

<p class="reading-time">Чтение: 12 минут</p>

Архитектура помогает локализовать изменения. Хорошая структура не угадывает будущее, а делает текущие зависимости видимыми.

!!! abstract "Фокус"
    - **Нужно знать:** ответственность, зависимости, модули, SPA и конфигурация.
    - **Часто в работе:** feature/domain/api boundaries, code review и паттерны React.
    - **Достаточно узнавать:** названия сложных архитектур без опыта их применения.

## Разделение ответственности

```text
ui -> feature -> domain -> api
```

- UI отображает данные и отправляет намерения пользователя;
- feature координирует сценарий;
- domain содержит правила предметной области;
- api общается с внешней системой.

Зависимости направлены в одну сторону. Сетевой модуль не должен импортировать кнопку.

## Модули и сборка

ES Modules используют статические `import` и `export`, поэтому сборщик может построить граф зависимостей и удалить неиспользуемый код.

Vite быстро запускает разработку через нативные ESM и собирает production bundle. Webpack гибко преобразует ресурсы loaders и plugins. Babel переводит новый синтаксис в совместимый JavaScript.

Create React App встречается в старых учебных и рабочих проектах, но для нового клиентского приложения обычно выбирают Vite или фреймворк. Важно уметь прочитать scripts, понять точку входа и собрать production-версию независимо от генератора проекта.

## SPA

SPA загружает оболочку и меняет представление на клиенте. Плюсы: плавная навигация и богатый UI. Риски: большой стартовый bundle, SEO, управление состоянием и ошибки сети. SSR и SSG могут вернуть HTML заранее.

## Паттерны React

- Container/Presenter отделяет данные от отображения;
- custom hooks выносят переиспользуемую логику;
- controlled component получает состояние и обработчики извне;
- error boundary изолирует ошибку рендера;
- composition передает части UI через children и props.

HOC и render props важно узнавать в старом коде, хотя hooks часто выражают ту же логику проще.

## Конфигурация

Секреты не попадают в клиентский bundle. Переменные окружения разделяются по средам, а публичные значения валидируются при старте.

## Code review

Проверяйте корректность, понятность, тесты, безопасность, доступность и влияние на производительность. Комментарий должен объяснять риск и предлагать проверяемое изменение.

!!! warning "Частая ошибка"
    Feature-Sliced Design, MVC или другая схема не делает проект хорошим сама по себе. Сначала определите границы и направление зависимостей.

## Как ответить на интервью

> Хорошая архитектура делает направление зависимостей понятным и локализует изменение. UI отображает состояние, feature координирует сценарий, domain хранит правила, api работает с внешней системой. Паттерн выбирают для конкретной проблемы, а не ради количества слоев.
